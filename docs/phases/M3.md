## Scope and boundaries

Persist event identity, build bounded/restart-safe `job_runs` projections, expose paginated failed/stalled
and worker-liveness data, and maintain/prune monthly raw-event partitions. Dashboard/UI is M4;
rollups, percentiles and alerts are M5. A disk spool is not M3 scope.
Telemetry remains best effort. Collector HTTP acceptance is not database durability; missing events
cannot be repaired by inventing job outcomes. Existing SDK transport and overhead budgets remain.

## Required prerequisite: durable event identity

`protocol.Event.ID` is present on the wire but M2 `WriteBatch` does not persist it. The current raw table
has a generated `id`, `ts`, `received_at` and `PRIMARY KEY(ts,id)`; none identifies a protocol retransmission.
Do not implement duplicate suppression by counting rows or treating the bigserial as the SDK event ID.

Before folding, record and implement a forward-only migration that preserves existing raw data:

- Store protocol event identity for new events. Define duplicate identity scope and behavior when the
  same ID is submitted with different content or timestamps; conflicts cannot silently overwrite data.
- Account for PostgreSQL partitioned unique-key restrictions: global deduplication may require a separate
  identity table or a documented bounded strategy. Decide this in an ADR before choosing the schema.
- Legacy rows have no recoverable protocol ID. Mark that fact; use their `(ts,id)` identity for replay,
  without claiming historical retransmission deduplication. Never generate IDs that imply SDK evidence.
- Upgrade an M2 database in place and test writer compatibility, COPY behavior, query indexes and
  migration re-entry. Document deduplication retention alongside raw/projection retention.

## Deterministic lifecycle folding

Use `(queue,job_id)` as the existing logical key only after documenting job-ID reuse/reset behavior.
Treat the reported `attempt` as identity/ordering evidence; duplicate `started` events must not increment
attempt counts. Define a total tie order and same-attempt state precedence in the ADR. An arbitrary
timestamp sort or arrival order is not enough for contradictory terminal events.

- The same supported event multiset yields the same projection across shuffles, duplicates, batching
  and restarts. Track distinct observed attempts; do not infer missing attempts were actually observed.
- A late event from a lower attempt cannot replace a later attempt's state. Retried/new-attempt evidence
  may supersede an earlier failure; retain earlier attempt history where available.
- Distinguish observed completed/failed/stalled state from inferred stale telemetry. A `failed` event
  alone does not prove retries are exhausted: the protocol has no `max_attempts` field.
- Missing enqueued/started/completed events leave timing fields unknown. Use supplied duration metadata
  for its documented meaning; timestamps from separate hosts do not establish accurate job duration.
- Queue-level `drained` telemetry is not a job transition. Preserve source state and evidence rather
  than applying every event to a fabricated job run.
- Define a durable processing checkpoint and projection update transaction. Sequence values are allocated
  before commit, so blindly advancing a global `id > checkpoint` cursor can miss late-committing batches.
  Account for that ordering, historical event timestamps and concurrent ingest. Bound reads, memory,
  query ranges and replay; expose lag and incomplete history instead of claiming a complete timeline.

## Failure and liveness evidence

Worker heartbeats use server receipt time and default to 15-second emission intervals.
Define worker down at 60 seconds without a receipt, detected by the next bounded evaluation tick;
this is a suspicion about telemetry availability, not proof the process or its job failed.
Document the evaluation interval so the actual bound is threshold plus interval, not an impossible
promise of detection before the threshold has elapsed.

Explicit `stalled` events establish observed stall evidence. A configurable lack-of-progress policy may
produce a separate suspected-stall view, with its threshold and reason shown. The protocol provides no
job-specific heartbeat or expected duration, so do not use '2 × expected duration' or worker liveness
as proof of a stalled job. Missing job telemetry is unknown. No terminal 'dead job' claim without new
explicit source evidence and a separately reviewed protocol change.

Expose data needed for these M3 checks through bounded paginated queries with stable ordering and auth.
Record exact paths/response schemas in the ADR and then OpenAPI when implemented. The general job
timeline/detail and dashboard API work remains M4; rollup queries remain M5.

## Retention and partition maintenance

- Default raw/history retention is 30 days. Define UTC cutoff, event-time versus receipt-time treatment,
  future/late timestamps and validation before deletion. Rollup retention is only implemented in M5.
- Drop a monthly partition only when its upper bound is at or before the cutoff: it must contain no
  unexpired rows. Coarse month retention can keep expired data for almost one extra month; document it.
- Prune terminal projections under the declared policy; unresolved/incomplete runs need a bounded,
  explicitly documented policy rather than indefinite growth. Late retained events must not resurrect
  pruned history as complete. Check projection/checkpoint lag before deleting unprocessed raw evidence.
- Create current plus the next two monthly partitions, including December/January boundaries. Startup
  and concurrent maintenance are idempotent; downtime recovery fills required gaps with bounded work.
- Use finite lock/statement deadlines and narrowly checked partition names/bounds. Never drop unrelated
  tables, volumes or databases. Migration testing uses disposable databases with seeded old/new rows.
