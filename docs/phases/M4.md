## Existing API and evidence

`GET /v1/queues` already returns live broker counts, update time, stale/error state and adapter errors.
It is currently unpaginated and has no historical throughput/failure-rate series. Its completed/failed
counts describe retained broker state, not monotonic counters; differencing them is not valid throughput
when jobs can be removed. Preserve the current response while specifying a compatible bounded dashboard
queue-page route or explicit page mode in ADR 0011.

M3 already has authenticated failure/stall/suspected-stall and worker pages. Reuse their evidence and
pagination semantics instead of building a second lifecycle model. Preserve default 100/max 200 items,
signed cursors bound to route/filter/evaluation time, C-order keys, finite query deadlines and nullable
lag/duration/retry-exhaustion evidence. New routes must be added to OpenAPI only when implemented.

All reads respect M3 identity, projection and retention policy: highest observed attempt/state precedence,
exact commit markers, unknown identity, possible reuse, contradictory facts, pruned history and tombstones.
No new protocol generation or terminal outcome may be inferred from a dashboard request.

## Query and timeline contract

- Implement queue detail, paginated jobs by documented observed state, and job detail with separately
  paginated retained attempts. A timeline page cannot load up to 32,767 attempts into one response.
- Use parameterized queries, bounded route identifiers, allowlisted sort/filter/window parameters and
  stable keys. Test Unicode, quoting, percent encoding and reserved route names; do not change producer
  identities by lowercasing or unsafe URL concatenation.
- Distinguish missing/pruned/temporarily-pruning history from a never-observed job. Return explicit
  unavailable/history-limited information where retained evidence allows it. A 404 is not proof that the
  production job does not exist. Do not bypass the M3 pruning fence to serve a half-deleted timeline.
- Render observed attempts and their supplied durations/errors. Missing starts/terminal facts or
  duration remain unknown; do not subtract clocks on different machines to manufacture duration.
- Preserve `source_states`, `state_evidence`, history flags, `retry_exhausted: null`, capture/receipt times,
  evaluation time and projection lag/consistency limitations in new responses and visible UI summaries.
- An explicit stall and a suspected stall are different. Worker silence means suspected worker down
  after the receipt/tick policy, not a dead worker or failed/exhausted job. Lag/telemetry loss remains visible.
- Keyset traversal is a live view. Inserts, state changes, late facts and pruning can change membership;
  do not promise an MVCC snapshot or full event replay history across pages.

## Metrics and the M4 performance gate

Before implementing overview rates, define their data source and denominator under ADR 0011. The proposal
uses selected retained attempt outcomes in an explicit UTC window: completion throughput counts selected
`completed` attempts per second; observed failure rate counts selected `failed` attempts divided by selected
`completed` plus `failed`. This describes retained selected outcomes, not all retry failures or complete
production-job history. Retried/superseded/contradictory outcomes and pruned/late evidence need visible
limitations; empty denominator is null. Broker depth/counts keep their own source/update/stale semantics.

Use bounded indexed projections/read queries, not raw history/metric scans or every browser page.
Existing capped projection-lag sampling remains a separate bounded evidence query. Set a maximum
lookback (proposal: 30 days), finite aggregation work/response size and explicit unknown-on-timeout behavior.
If summaries cannot support truthful rates within budget, accept an explicit M4 read-model design before
adding it; do not silently implement M5 hourly percentiles/analytics or relabel a broker count as a rate.

Retain **dashboard p95 query < 300 ms**. The previous 30-days-of-hourly-rollups workload belonged to M5,
whose rollups do not exist. For M4, benchmark queries over 30 days of retained M3 summaries with a declared
representative dataset and concurrent projection/maintenance. The proposal starts at 100 queues,
100,000 jobs and 300,000 attempts; record hardware, row counts, indexes, query plans, cache state and
sampling. The threshold is unchanged. The hourly-rollup workload becomes an additional M5 gate after
QL-023, not evidence assumed to exist now. Report all request/error/timeout counts. Failures or unavailable
rates fail the benchmark run; they cannot be excluded to manufacture a passing latency result.

## Browser access and rendering

The API/SDK currently share `QUEUELENS_ADMIN_TOKEN` (legacy `QUELENS_*` configuration aliases remain).
Keep this contract. Choose an authenticated same-origin proxy/session design that holds the server token
outside frontend assets/browser persistence and restricts dashboard credentials to read routes.
Do not bundle an ingest/admin secret into JavaScript, URLs, local/session storage, error logs or analytics.
Define bootstrap, expiry/logout and deployed/development cookie behavior before scaffolding auth.

Render job/queue/error metadata as text; treat it as untrusted even after protocol best-effort redaction.
No raw HTML or execution of recorded commands. Provide loading, empty, error, unauthorized, stale, missing
and history-limited states, accessible keyboard navigation and readable layouts at narrow widths.

Every dashboard list, including queues/workers/attempts, uses bounded pagination. Bound cached pages and
response bytes. Poll at a documented cadence (proposal: five seconds), with at most one request per view,
abort on route/filter changes, discard older responses and release timers/subscriptions on unmount.
Specify hidden-tab/backoff behavior; network errors keep the last data visibly stale rather than show zeros.
